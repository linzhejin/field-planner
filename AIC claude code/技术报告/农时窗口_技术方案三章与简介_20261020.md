# 农时窗口技术方案三章与简介

本稿对应附件2的第一、第三、第六章，可直接并入技术方案。按2026年10月20日代码基线 e902f70 和已保存的公开运行记录撰写。文中证据编号用于团队核对，定稿时转为附录引用。本文未使用独立候选题或参考答案。

## 一 作品概述

### 背景介绍

油菜苗期田间管理需要结合苗情、墒情和沟渠状态判断。公开技术指导意见分别讨论苗期、冬前以及持续阴雨等情境，所述措施带有地区、阶段和田况条件。同一段技术文字不能仅凭“油菜”关键词就转换成对所有地块都有效的处置指令。例如，记录苗情与实施间苗不是同一任务，看到降雨预报也不能直接确认田间积水。农时窗口据此把“依据是否适用”和“当前是否需要作业”分开处理。[证据E1、E2]

本作品采用公开文献研究和开发验证形成设计，目前没有农户实地调查或田间应用效果数据。面向湖北已确认进入苗期的油菜地块，作品尝试解决一个有限问题：用户怎样把已确认的农情、个人需求和可作业时间整理成可解释的七天安排，并在情况变化后保留完成事实、查看调整原因。[证据E2、E3]

### 目标定位与创新主张

用户从一块地开始建档，需要时新增其他地块。系统围绕巡田观察与有条件的既有沟渠维护候选提供依据、缺项和安排；当前采用一名执行者、每块地独立排程，分别生成的计划不保证合并后可执行。跨地块联合排程、其他个人待办、多作物和药肥处方暂不纳入本轮。[证据E3、E4]

作品的应用创新主张有两点。第一，把农业资料适用性、任务必要性、每日作业窗口和最终排程结果作为不同状态表达，避免“找到资料”直接变成“必须执行”。第二，把语言理解与确定性计算分工：模型组织追问、解释和工具调用，程序校验输入并负责约束计算、事实保存与版本管理。这些是可由代码和案例核对的设计特点，不是已经证明优于其他方法的性能结论。[证据E4、E5]

预期技术目标包括：不在缺少关键条件时生成确定处置；已排任务满足本地工时、连续时段和前置约束；现场反馈后保留已完成记录；引用能够定位原件与适用限制。目标实现程度应分别用开发测试、独立对照和操作体验衡量。目前尚无完整独立对照成绩，不报告增产、节肥或经济收益。[证据E6、E7]

## 三 AI技术工具选择与运用

### 模型与工具分工

系统使用兼容 Chat Completions 的 DeepSeek 服务作为对话主智能体，模型配置由环境参数读取。工具集合包括读取地块、检索资料、评估任务、查询天气和地点、提出档案或现场反馈修改、生成计划预览。修改建议经用户确认后进入持久化流程；计划预览与采用分别处理。选择这一方式，是为了允许自然语言输入，同时让关键事实和计算结果接受结构化校验。[证据E5、E8]

已有一次保存的真实服务记录显示，配置为 deepseek-flash 的会话成功调用 read_field 和 evaluate_field；同批记录中的 Open-Meteo 返回武汉七天预报。这证明该次服务连接和有限工具调用可用，不等于所有多轮流程或失败情境均已完成真实验收，也不保证后续服务始终可用。[证据E9]

### 农业证据与规则处理

项目保留31张C卡、原始来源索引与文件指纹，核心七卡另设采用登记。当前拟定口径为：C11、C31只用于观察记录；C23只用于有依据、已确认问题与需求并具备作业条件的既有沟渠维护候选；C18、C19、C20、C24暂缓自动应用。补充来源使用A04前缀单独登记，不改写原卡或原始文件。[证据E1、E10]

这套有限用途结论已由负责人依据AI辅助意见授权确认，李思默独立复核仍待完成，运行登记的 formal_adopted 当前为0。负责人授权未被记作逐条人工查阅。2026年10月20日的公开样本自检确认九条引文可在登记页定位，2026年10月22日（提交 bc9abb7）已修复：暂缓卡与限用途卡标签在四个出口（检索、详情、模型输出、导出）统一区分，并新增来源年份/地区/阶段/田型/干湿摘要。因此，本稿不把“资料可追溯”写成“全部农业判断已经审核通过”。[证据E10、E11]

### 排程与状态保存

项目使用Python 3.12、Streamlit界面和SQLite本地存储。程序在已确认范围和需求的基础上检查每日现场、天气作业条件、可用分钟数、连续时段及前置关系，再形成安排。天气预报用于风险信息，不自动写成已发生降雨或田间积水；用户提供的未知值保持未知。[证据E4、E12]

现场反馈和计划版本分开保存。完成事件先记录，重排结果通过预览展示，用户采用后形成新版本。相关开发测试覆盖保存后重开、重复完成拒绝、取消预览不丢事实、不同地块互不覆盖等行为；这些测试证明特定输入下的工程性质，不能替代真实使用体验。[证据E6、E8]

### 对照验证安排

统一运行器为直接生成、加检索、完整系统三组保留输入、输出、错误、耗时与调用记录。当前公开开发记录只包含本地C组运行，A/B真实模型结果尚未齐全；其中还出现输入校验为invalid而记录状态为executed的条目，需工程方明确处理口径。正式比较前应固定模型配置、工具条件、天气快照和判分规则，保存首次失败，不用重试成功覆盖初测。[证据E7、E13]

计划中的独立候选包含30个主案例与6个边界案例。只有完成复核、固定版本并实际运行后，才能填写正式结果。组别编码需要由评测组织者私下保管映射；仅把A/B/C改写成固定可识别的g1/g2/g3，不能自动证明盲评有效。[证据E7、E13]

## 六 总结与展望

### 经验总结与现阶段结论

农时窗口已经形成围绕地块、事实、任务和计划版本的工程实现，并保存了公开开发验证及有限的真实服务调用记录。当前可以陈述的是：关键计算有程序入口，来源有定位记录，反馈与计划采用有独立流程。尚不能陈述的是：对照效果已经显著提升、所有引用适用性验收完成、目标农户已经认可，或田间生产获得收益。[证据E4至E13]

本阶段最需要关闭的差距包括：七卡独立复核与正式采用验收、独立案例复核与正式运行、实际页面验收及体验记录。开发测试通过与农业文献逐字定位应分别记录；AI辅助整理不得代替成员本人独立判断，用户操作测试也不得冒充农业专业审核。[证据E6、E10、E11]

### 后续改进

近期先完成已有范围的证据与验收：修正引用展示，复核规则用途，固定独立测试材料，并保留成功、失败和分歧记录。报告中的效果章节据实际结果补齐，达不到目标时如实说明限制或缩减能力。[证据E3、E7、E11]

在当前核心流程完成验收后，再评估跨地块共享时间协调、更广生育期和作物范围。扩展需要新的适用证据、数据字段和未见案例；面向真实生产的进一步应用还需要目标用户体验及适当的农业专业和田间验证。这些内容是后续计划，未计入本轮已完成成果。[证据E3]

## E02名称与简介

名称建议：**农时窗口**

简介建议：

农时窗口面向湖北油菜苗期管理，结合用户确认的农情、作业需求和可用时间，提供巡田观察与有条件的既有沟渠维护候选，并生成单地块七天安排。系统由对话智能体组织追问和解释，以可追溯资料与程序约束核对条件、计算排程；现场反馈后保留完成记录，展示调整原因和计划版本。当前已形成工程原型并保存有限真实服务调用记录，规则签认、独立对照和体验测试仍在推进，尚未验证田间生产收益。

该简介为当前进度口径；正式提交前按完成的验证结果更新，不提前写入成功率或效益。
